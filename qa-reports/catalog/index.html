K1First Launch — Native Onboarding9 case
Kategori notu
The first-launch chain: privacy consent -> policy -> consent again -> the OS
notification permission. Three of those four dialogs are ours; the last one
belongs to the operating system, and the difference matters in every case here.

TWO WAYS TO REACH THE CHAIN, AND THEY PROVE DIFFERENT THINGS
------------------------------------------------------------
`_ranThisSession` is a STATIC field, so onboarding replays only when the process
restarts. That gives two routes, used deliberately:

  session.cold_start()               a real launch. Only NP-01 uses it, because
                                     "a real launch shows consent" is the only
                                     claim that needs it, and it costs ~20s.
  FirstLaunchFlow.RestartFlowNow()   replays from consent with no relaunch. Used
                                     by NP-03..NP-05 and NP-08/09, which are
                                     claims about the chain's INTERNAL logic,
                                     not about launch behaviour. It also skips
                                     ShouldRun(), which is what lets those cases
                                     run in the Editor at all.

No case here asserts anything absolute about the counters. Both routes leave
ConsentShownCount/PolicyShownCount wherever the previous case left them, so
every count is measured as a DELTA around the action under test. An absolute
assertion would pass or fail depending on case order, which is the definition
of a test that measures the harness instead of the product.

WHY NP-06 IS THE DENY PATH AND NP-07 IS ALLOW
---------------------------------------------
Order, not preference. Whichever runs last leaves the device in that state, and
every later category (and LC-07's "already granted, no dialog" claim) is happier
with notifications ON. So deny is measured first and allow last.

PLATFORM REACH
--------------
  NP-01, NP-02      device only     - no cold start / no OS view in the Editor
  NP-06, NP-07      Android only    - re-arming the OS dialog needs
                                      `pm reset-permissions`; an iOS device has
                                      no equivalent, so these SKIP with that
                                      reason rather than silently passing
  the rest          everywhere

Case list:
  NP-01  A real cold start shows the consent dialog
  NP-02  While it is up, AltTester is blind (the view is the OS, not Unity)
  NP-03  "Read policy" opens the policy dialog and does NOT accept consent
  NP-04  Closing the policy brings consent BACK — consent is never assumed
  NP-05  Accept moves the flow past consent and records acceptance
  NP-06  Deny  -> PermissionResult 'Denied',  Settings toggle OFF
  NP-07  Allow -> PermissionResult 'Granted', Settings toggle ON
  NP-08  The finished flow shows no leaked dialog (shown == resolved)
  NP-09  Watchdog negative: nothing on screen once the flow is Done

WHY IT RUNS FIRST
  A genuine first launch happens once. Every later category needs the screen
  clear of onboarding, so setup drives the chain to Done before any case runs
  — which means the ONLY place these claims can be made honestly is here, from
  NP-01's own cold start, before anything else has touched the app.

NO BASELINE RESET FOLLOWS
  The game state this category leaves behind is a freshly launched app, which
  is what the next category wants anyway. Wiping a wallet that a cold start
  already emptied is cost without a claim.

Both channels VERIFY themselves rather than trusting a return code: the
interruption re-reads the foreground and raises if the app still owns it, and
the kill re-reads the app state and raises if the process survived. A case that
believes it was interrupted, and was not, would go on to assert that state
survived an event that never happened — the most expensive kind of green.

WHAT MAKES LC-02 THE CASE WORTH WRITING
---------------------------------------
`NativeProbe.PendingPurchaseToken` is non-empty exactly while a purchase dialog
is open and unresolved, and its own comment says it survives a background round
trip. LC-02 is what makes that a tested promise instead of a claim in a
docstring: background the app mid-purchase, come back, finish the purchase, and
the wallet must move by the pack's coins ONCE. A resume that re-delivers a
receipt is the classic IAP double-credit, and it is invisible to every other
category in this suite.

WHO ASKS WHOM, WHILE A DIALOG OWNS THE SCREEN
---------------------------------------------
LC-02 and LC-03 are sequenced around a measured platform behaviour rather than
against it. Measured on emulator-5554, 2026-08-20, six times, identically:

  dialog opens, app stays in front   Unity RUNS. AltTester reads
                                     PendingPurchaseToken through the main
                                     thread while the dialog is up — a dialog
                                     alone does not pause the game
  app is backgrounded                Unity pauses. onPause, then
                                     OnApplicationPause(True). Ordinary
  app is brought back, dialog still  Unity STAYS paused. onResume arrives,
  on screen                          'windowFocusChanged: true' does not, and
                                     OnApplicationPause(False) therefore never
                                     fires. The AlertDialog is a separate
                                     window and keeps focus across the trip
  the dialog is answered             Unity resumes where it left off, in
                                     0.1-0.5s, every time

So the pause is started by the BACKGROUNDING and extended by the dialog. Worth
stating precisely, because "a native dialog pauses the game" is the intuitive
reading and it is not what happens.

SPEC, not a defect — and deliberately not engineered around. The state is
harmless here: the dialog covers the screen, so nobody sees a frozen game
behind it; answering it resumes cleanly; the wallet is exactly right either way
(LC-02 proves the credit lands once, LC-03 that the trip answers nothing).

A SHIPPING product would likely dismiss the dialog itself on backgrounding, so
the player returns to a clean screen with no stale question on it. That is a
product decision this repo has no reason to make: YarnLoop Dummy exists to
prove the Appium x AltTester pairing works and to carry that know-how to real
projects, not to be a game with a release-quality lifecycle. Building the
dismissal here would add product surface without adding evidence about the
pairing.

What the pairing DOES get out of this state is the point: it is the cleanest
demonstration in the suite of why both drivers are needed. Unity cannot answer
while the dialog holds focus, and Appium can — so the cases below read the
screen through Appium and the game through AltTester, each where it is the only
observer that can see. The resume wait is measured and noted on every run, so
the day the behaviour changes, the report says so.

What it does change is WHICH OBSERVER each step may use, and the two cases are
ordered so that no step needs the one that cannot answer:

  wallet + counters   read BEFORE the dialog exists, when Unity is guaranteed live
  the dialog itself   read through Appium ALONE while Unity is parked
  the answer          delivered through Appium — Buy or Cancel, as the user would
  game state after    read through Unity, which by then is running again

Reading the wallet up front is not a convenience. It is the only moment in
either case when the answer is guaranteed to be obtainable.

WHY A COLD START MUST FIND AN EMPTY WALLET
------------------------------------------
`CoinWallet.Awake` says it in the product code: "Persistence intentionally
disabled — every app launch / editor Play starts fresh. PlayerProfile stays as
an in-memory DTO; the file APIs are not called." The file APIs exist — Load(),
Save(), a JSON path under persistentDataPath — and are deliberately not wired
up. LC-06 pins that decision down. The day someone wires Save() in, LC-06 turns
red on purpose and names the change, instead of the suite silently starting to
carry balances between runs.
